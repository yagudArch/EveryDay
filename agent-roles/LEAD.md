## Git workflow и приёмка задач

LEAD обязан соблюдать и обеспечивать для MOBILE, BACKEND, AI ENGINEER и QA/DEVOPS единый регламент AGENTS.md (разделы 9 и 14) и MASTER_PROMPT.md (разделы 48 и 49):

`git status → работа → тесты/build → git diff → git add → git commit → git push → git status`

- Для каждой задачи с изменениями, включая MD/.ai, **commit обязателен и push обязателен**. Commit без push не считается завершением. После push обязательны подтверждение отправки и чистый git status, включая отсутствие untracked файлов.
- Перед каждым commit проверить `git config --get user.name`, `git config --get user.email`, `git var GIT_AUTHOR_IDENT`, `git var GIT_COMMITTER_IDENT`; не менять identity на выдуманную и не перенастраивать глобальный Git.
- Проверить diff и staged diff, адресно добавлять только согласованные изменения задачи. Случайные, временные и чужие изменения не включать, даже если они уже staged. LEAD согласует владельцев файлов и последовательное выполнение Git-операций в общем рабочем дереве.
- Не принимать задачу и не подтверждать DONE без результатов тестов/build, SHA, подтверждённого push в целевую ветку и чистого итогового git status. Собственная задача LEAD проходит те же проверки; финальный отчёт получает заказчик.
- При невозможности commit/push или чистого статуса задача не завершена. Установить BLOCKED, сохранить диагностику и требуемое действие в `.ai/ACTIVE_WORK.md` и статусе задачи. Исполнитель эскалирует LEAD; LEAD сообщает заказчику. Не заменять эскалацию одним обновлением файла, не скрывать блокировку и не удалять чужую работу ради чистоты.
- До основного commit синхронизировать относящиеся к задаче `.ai/*`, оставляя REVIEW до подтверждения Git-результатов. Если после push обновлены записи о закрытии, проверить и отправить их отдельным commit/push; финальный отчёт — только после повторного чистого git status.
- Поддерживать согласованность AGENTS.md, MASTER_PROMPT.md, всех agent-roles/*.md и `.ai/*`. Ролевые инструкции не могут отменять этот обязательный минимум; изменение процесса вносить согласованно, без изменения архитектуры или повторной инициализации.
